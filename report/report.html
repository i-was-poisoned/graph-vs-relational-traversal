Graph vs. Relational Traversal

At what traversal depth, and at what data volume, does a property graph model outperform an equivalent normalized relational model for the same query?

Pedro Santos Faustino

Interim report
November 2026

1. Infrastructure

Before measuring anything, we built the tools to get the data, load it into the two databases in exactly the same way, and check that it is correct. This chapter describes that infrastructure. It is now complete and tested, so the next chapters are about measurements.

1.1 The question and the data

The project asks: at what traversal depth, and at what data volume, does a graph database answer the same question faster than a relational database? To answer it, both databases must hold the same data and run on the same computer, so that the only difference is the model.

The data comes from GH Archive, which publishes one file for every hour of public activity on GitHub. Each line of a file is one event, for example a person pushing code to a repository. From each event we keep only who did it (the actor) and where (the repo). Two actors are connected when they worked on the same repo. Bot accounts are removed, because they connect thousands of unrelated repos.

1.2 The data model

The same model is built on both sides:

ConceptPostgreSQL (relational)Neo4j (graph)
Actortable actor (id, login)node :Actor (id, login)
Repotable repo (id, name)node :Repo (id, name)
Connectiontable actor_repo (actor_id, repo_id)relationship INTERACTED_WITH
Keysprimary keys and an index on repo_iduniqueness constraints on the ids

There is one connection per actor and repo pair: ten pushes by the same person to the same repo count as one connection.

1.6 Two processes

Manual pipeline. You choose the hours. Each choice goes into its own database, named after the data it holds, for example gharchive-2026-08-27-15-3h (three hours starting on 27 August 2026 at 15:00 UTC). Before loading, the database is deleted, created again and checked to be empty. This process gives the fixed data sets used for the measurements.

Automatic pipeline. Task Scheduler checks every 15 minutes. Once a day, as soon as the computer is on and both databases answer, it reloads gharchive24h with the last 24 hours. It shows how a scheduled data pipeline works, but it is not used for the measurements, because its data changes every day.

2. Measurement plan

The measurements grow step by step. We start with a small amount of data, measure, and only then add more. At each step the same traversal is run in both databases, and the results are written down in this report before moving on.

Table 2. Each step adds data from the same day, so only the volume changes.

We use a weekday because it has much more activity than a weekend, so the graph is better connected. The exact hours for steps 3 and 4 will be chosen when we get there.

2.2 What we do at each step

  1. Load the data with the manual pipeline (build_hours.py) and check that both databases hold the same counts.
  2. Run the traversal at increasing depths (1, 2, 3, … hops) in SQL and in Cypher.
  3. Check that both databases return the same answer. If they don't, the timing is not compared.
  4. Measure the time from Python, several times, with a time limit.
  5. Write down whether each query finished, failed or ran out of time. A query that cannot finish is also a result.

2.3 What we record

  • the exact queries (SQL and Cypher);
  • the counts at each depth, for both databases;
  • the times, and the calculations made with them (for example, the median of the repetitions);
  • what we find, in plain words;
  • screenshots, for example of the graph in Neo4j.

3. How the two databases are compared

This chapter explains what is measured, and how the measurements decide which database is better, and from which depth. It replaces the general ideas of chapter 2 with the method actually used by the scripts.

One change to the plan of chapter 2: the first measurements showed that one hour of data is too fragmented (99.3 % of the actors share no repository with anyone, and the largest group of connected actors has only 8 actors), so there is nothing deep to traverse. The measurements therefore start at 6 hours and grow from there (24 hours, 3 days, up to a week), always from the same day.

3.1 The question asked at each depth

From one starting actor: how many different actors can be reached in at most N hops? One hop goes from an actor to a repository it worked on, and from that repository to another actor who also worked on it (actor → repo → actor). So every hop crosses two connections, and the work grows with every hop:

Depth (hops)PathJOINs in SQLRelationships followed in Cypher
1actor → repo → actor22
2… → repo → actor44
3… → repo → actor66
4…88
5…1010
6…1212

Table 3. Every hop adds two JOINs in SQL and two relationships in Cypher.

This is the heart of the research question: in a relational database every extra hop means joining tables again, while a graph database follows connections that are already stored next to each node. The deeper the traversal, the more this difference should show.

3.2 The queries

Both databases must give exactly the same answer at every depth; a time is only compared when they do. In SQL, the number of hops isn't known when the query is written, so a recursive query is used: it starts from the actor and repeats the two JOINs once per hop, keeping each actor only once per level. 

WITH RECURSIVE reach(actor_id, depth) AS (
    SELECT :start, 0
    UNION
    SELECT ar2.actor_id, r.depth + 1
    FROM reach r
    JOIN actor_repo ar1 ON ar1.actor_id = r.actor_id   -- actor -> repo
    JOIN actor_repo ar2 ON ar2.repo_id  = ar1.repo_id  -- repo  -> actor
    WHERE r.depth < :depth
)
SELECT count(DISTINCT actor_id) FROM reach WHERE actor_id <> :start

In Cypher, two versions are measured, because the first results showed that the way the query is written matters as much as the database:

  • paths: the natural way to write it, one pattern repeated 1 to N times. Neo4j follows every path and removes repeated actors only at the end. Two actors who share 27 repositories are joined by 27 paths, then 27 × 27, and so on.
  • levels: level by level, like the SQL. Each step starts from the actors found in the step before and keeps only actors never seen before.
// paths, depth 3
MATCH (a:Actor {id: $start})
      ((:Actor)-[:INTERACTED_WITH]->(:Repo)<-[:INTERACTED_WITH]-(:Actor)){1,3}
      (b:Actor)
WHERE b <> a
RETURN count(DISTINCT b)

Comparing levels with the SQL compares the two databases using the same method; comparing paths with levels shows the cost of writing the query the obvious way.

3.3 Where the traversals start

The starting actors are chosen by a script, never by hand, so that the choice can't favour one database. For every volume of data, two groups of 10 actors:

  • top: the 10 actors connected to the most other actors in one hop (the hardest case, where a traversal grows fastest);
  • median: the 10 actors whose number of connections is closest to the median (a typical actor).

Ties are broken by the number of repositories, then by the smaller id, so the choice never changes. Both databases must choose exactly the same 20 actors.

3.4 The four measurements

A database is better if it gives the same answer with less of four things. Each of them is measured in both databases, for every starting actor, every depth and every volume:

WhatHow it is measuredWhy it matters
1. Data processed How many data pages the database went through to answer, in MB. Both databases store data in pages of 8 KB, so the numbers can be compared directly. Reported by EXPLAIN (ANALYZE, BUFFERS) in PostgreSQL and PROFILE in Neo4j. The part read from disk is recorded separately. The amount of work each model needs for the same answer, whatever the speed of the computer.
2. Time Seconds, measured from Python: the median of 5 runs. The first run is recorded apart, because it includes preparing the query. Each run has a limit of 60 seconds. The most visible result: how long a user waits.
3. Space The memory the query used while it ran (in MB), what PostgreSQL had to write to disk because it didn't fit in memory, and the size of each database on disk. A database can be fast by using a lot of memory; and the same data can take more or less room in each model.
4. Computing power The CPU seconds used by the database server during the query, read from the operating system before and after each run; and CPU seconds ÷ time, which says how many processor cores worked at the same time. Time alone hides whether a database is fast because it works less, or because it uses several cores at once.

Table 4. The four things compared at every depth.

Four more facts are recorded with every result, so it can be trusted:

  • whether both databases gave the same answer (if not, the result is not used);
  • whether each query finished, ran out of time, or was skipped because it had already run out of time at a smaller depth (a query that can't finish is a result too);
  • whether the result is reliable: the measurements are made on a laptop that is also used for other work, so a result is flagged when the computer was busy (CPU above 80 %) or the 5 runs were very uneven (the slowest more than 3 times the fastest). To reduce this, the order of the databases changes on every run, and large volumes are measured when the computer is quiet;
  • the size of the data: the hours loaded and from when, and the number of actors, repositories and connections.

3.5 How the results decide the question

For every volume of data, the results are read in this order:

  1. Check the answers. Only lines where both databases gave the same number of actors are compared.
  2. Who is faster at each depth. For each depth, the median time of the 10 top actors and of the 10 median actors, in each database, and how many times faster the winner was. When one side ran out of time, the other side was at least 60 s ÷ its time faster.
  3. The crossing depth. The smallest depth from which Neo4j is faster for most actors and stays faster at every greater depth. This is the answer to “from which depth” for that volume.
  4. Why. The data processed, the memory and the CPU explain the times: a database that is faster because it processes less data has a real advantage; one that is faster only because it uses more memory or more cores has a different one.
  5. Across volumes. Putting the volumes side by side (6 hours, 24 hours, 3 days, …) shows whether the crossing depth moves as the data grows. This is the answer to “at what data volume”.

Both Cypher versions are read this way. The levels version gives the fair comparison of the two databases; the paths version shows what happens when the query is written the natural way.

3.6 Where the results are kept

Every measurement writes one CSV file in the folder results/, named after the database and the moment it was measured, for example gharchive-2026-10-08-9-24h_2026-11-19_14-05-12.csv. Each line answers one question (one starting actor, one depth, one Cypher version) and has three parts: first the test (the data, the date, the hours, the number of actors, repositories and connections, the starting actor and the depth), then a PostgreSQL block and a Neo4j block with exactly the same columns, and finally which database was faster and by how much. Every column is explained in the project's README.
